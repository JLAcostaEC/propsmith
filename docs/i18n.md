# i18n

Optional, and off by default. The core carries plain English and a stable id per member; an adapter
turns that into whatever your tool speaks.

Delete the `i18n` block and the whole lane disappears — no lockfile, no catalog checks, no
`catalog-*` diagnostics. Nothing about the tables changes.

## Turning it on

```ts
import { defineConfig } from "@jlacostaec/propsmith";
import { paraglide } from "@jlacostaec/propsmith/i18n/adapters";

export default defineConfig({
  sources: ["src/**/*.{ts,svelte}"],

  outputs: [
    { name: "site", files: ["docs/**/footer.svx"], description: "i18n" },
    { name: "llms", files: ["docs/**/llms.md"], description: "text" },
  ],

  i18n: paraglide({
    project: "./project.inlang",
    stalePath: "./messages/{locale}.stale.json",
  }),

  lockfile: "./propsmith.lock.json",
});
```

`description: "i18n" | "text"` per output is the entire i18n surface at the rendering level. An
output marked `"i18n"` gets the adapter's expression in the Description cell; one marked `"text"`
gets plain English. The example above is the common shape: a translated docs site and an
untranslated `llms.md`, from one run.

`description: "i18n"` with no `i18n` block fails config validation.

The `import * as m from "$lib/paraglide/messages"` in the target file is yours to write, once per
file. propsmith only touches what is between markers.

## What becomes a key

Everything a translated cell contains is a message — a cell that is half translated is a bug:

| text                                | key                                   | example                              |
| ----------------------------------- | ------------------------------------- | ------------------------------------ |
| a prop's description                | `<component>_props_<prop>`            | `button_props_size`                  |
| a description inherited from a type | `global_types_<type>`                 | `global_types_variant`               |
| a `@deprecated` reason              | `<component>_props_<prop>_deprecated` | `button_props_appearance_deprecated` |
| the word introducing that reason    | `propsmith_deprecated`                | `propsmith_deprecated`               |

So this:

```ts
/** @propsmith Button */
export type ButtonProps = {
  variant?: Variant;

  /**
   * Visual style of the button.
   * @deprecated Use `variant` instead.
   */
  appearance?: string;
};
```

writes this catalog:

```json
{
  "button_props_appearance": "Visual style of the button.",
  "button_props_appearance_deprecated": "Use `variant` instead.",
  "global_types_variant": "The visual style of a control.",
  "propsmith_deprecated": "Deprecated"
}
```

and this cell:

```md
| ~~`appearance`~~ | `string` | | {m.button_props_appearance()} **{m.propsmith_deprecated()}:** {m.button_props_appearance_deprecated()} |
```

Two consequences worth knowing:

- **An inherited description is one key for every prop that shares it.** Ten components typed
  `Variant` translate one message, not ten. See [types](./types.md#inherited-descriptions).
- **A prop with no description produces no key**, and its cell stays empty rather than calling a
  message that would not exist.

Adapters may rename all of these through `key(ctx)`, which receives
`{ component, prop, kind, type? }`. Return a distinct key per `kind`, or two texts overwrite each
other in the catalog — propsmith reports that as an `invalid-key` error rather than letting it
happen.

## The `I18nAdapter` interface

```ts
/** locale -> key -> text */
export type Catalog = Record<string, Record<string, string>>;

export interface I18nAdapter {
  name: string;
  locales(): { source: string; all: string[] };
  load(): Catalog;
  save(catalog: Catalog): void;
  /** The expression written into the markdown cell, e.g. `{m.the_key()}`. */
  expression(key: string): string;
  /** `null` when the key is legal, otherwise the reason it is not. */
  validateKey(key: string): string | null;
  /** Key naming. Defaults to the table above. */
  key?(ctx: KeyContext): string;
  /** Where invalidated translations are parked. `{locale}` is substituted. */
  stalePath?: string;
}
```

Only four things vary between i18n tools: where the catalog lives, which locales exist, what
expression goes in the markdown, and which keys are legal. **The staleness algorithm is core, not
per-adapter** — an adapter reads, writes and speaks its tool's syntax; it never decides what is
stale.

Writing one is in [adapters](./adapters.md#a-custom-i18n-adapter).

## The paraglide adapter

Ships as a subpath export, `@jlacostaec/propsmith/i18n/adapters`, with no extra dependencies.

```ts
paraglide({
  project: "./project.inlang",
  stalePath: "./messages/{locale}.stale.json",
});
```

| option       | default                            | effect                                    |
| ------------ | ---------------------------------- | ----------------------------------------- |
| `project`    | `"./project.inlang"`               | the inlang project directory              |
| `key`        | the table above                    | key naming, given the `KeyContext`        |
| `expression` | `` `{m.<key>()}` ``                | what goes in the cell                     |
| `stalePath`  | `"./messages/{locale}.stale.json"` | where invalidated translations are parked |

It reads `project.inlang/settings.json` for the locale list and for `pathPattern`, so nothing is
duplicated in propsmith's config. `validateKey` rejects anything that is not a JavaScript
identifier, because in paraglide the key becomes a function name.

## The lockfile

Three texts are alive at once: the English in the JSDoc (**A**), the English in `en.json` (**B**),
and the translation (**C**). The question that matters — _was C translated from the English that is
there now?_ — is answerable from neither A nor B, because `en.json` is an output that gets
overwritten.

So propsmith commits `propsmith.lock.json`:

```json
{
  "version": 1,
  "keys": {
    "button_props_size": {
      "source": "src/shared/ui/button/button.types.ts#ButtonProps.size",
      "en": "a3f1c2d4",
      "locales": { "es": "a3f1c2d4" }
    }
  }
}
```

`keys[k].en` is the hash of the English propsmith last wrote. `keys[k].locales.es` is the hash of
the English **the Spanish was translated from**. That second field turns one bit into a complete
truth table:

| JSDoc vs `lock.en` | `en.json` vs `lock.en` | meaning                           | action                                                                      |
| ------------------ | ---------------------- | --------------------------------- | --------------------------------------------------------------------------- |
| =                  | =                      | nothing changed                   | nothing                                                                     |
| ≠                  | =                      | the JSDoc changed                 | rewrite `en.json`, invalidate translations                                  |
| =                  | ≠                      | **someone hand-edited `en.json`** | warn: it is generated, move the text to the JSDoc. Leave translations alone |
| ≠                  | ≠                      | both changed                      | `catalog-conflict`: the JSDoc wins, and the divergence is reported          |

Row three is the reason the file exists. Comparing the JSDoc against `en.json` directly collapses it
into row two and destroys a valid translation over someone's typo fix.

Keys are readable rather than content-addressed (`button_props_size_a1b2c3d4`) because in paraglide
the key _is_ the function name: a typo fix in a sentence would otherwise rename it across every
locale **and** rewrite the table that calls it.

**Merging.** `locales.*` is the only value in the file that cannot be recomputed from source, so a
conflict there is resolved by keeping both sides, never by regenerating. Keys are written
alphabetically and each locale gets its own line, which keeps conflicts small.

## Stale translations

When the English behind a key changes, the existing translation is not deleted and not left
pretending to be current. It moves to `messages/{locale}.stale.json`.

**The presence of a key in that file is the review queue.** If `es.stale.json` is empty, Spanish is
current.

`check` reports each one as a `catalog-stale` warning rather than an error, because `write` has
already invalidated it and CI's machine translation refills it on the next run. `--strict` promotes
it, which is what you want when freezing a catalog before a release.

## Build ordering

**propsmith writes the catalog and stops.** It does not run `paraglide-js compile` — that is your
build, and running it for you would mean knowing your outdir, project path and bundler.

```jsonc
"scripts": {
  "docs": "propsmith",
  "docs:check": "propsmith check",
  "build": "propsmith && paraglide-js compile --project ./project.inlang && vite build"
}
```

1. `propsmith` writes `messages/en.json` and the tables containing `{m.button_props_size()}`.
2. `paraglide-js compile` turns the catalog into the `m` module.
3. `vite build` resolves the calls.

Out of order, step 3 fails on a missing export — loudly, which is the right failure.

## Migrating an existing catalog

If your prop descriptions already live in the catalog and the tables already pair each prop with its
message key, the migration is mechanical:

1. Extract inline object types into named ones first. Useful whether or not you migrate.
2. Move each English string from the catalog into the JSDoc of its member, renaming the key to
   `<component>_props_<name>`. The existing tables tell you which key belongs to which prop.
3. Move descriptions that repeat across components onto the shared type instead, and let the props
   inherit them — one key each, not one per component.
4. Let CI's machine translation fill the gaps.
